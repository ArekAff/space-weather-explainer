# Repository conventions: folder types and the practices each follows

Written 2026-11-14 after a web search for published conventions per folder type. For every type: the sources, what
the repo does, and where it deliberately differs. Change a convention here first, then in the folder's `CLAUDE.md`.

## 1. Application code: `code/` (Python, uv workspace)

Sources: uv documentation, "Workspaces" (https://docs.astral.sh/uv/concepts/projects/workspaces/); pydevtools
handbook, "How to set up a Python monorepo with uv workspaces"
(https://pydevtools.com/handbook/how-to/how-to-set-up-a-python-monorepo-with-uv-workspaces/).

| Practice | Here |
|---|---|
| One workspace root, one shared lockfile and environment | `code/pyproject.toml`, `code/uv.lock`, `code/.venv` |
| Each member is its own package with a `src/` layout and its own `pyproject.toml` | `code/ingestion/src/swx_ingest/`; `platform` joins the same way |
| Shared dev tools (ruff, pytest) and their settings at the workspace root | `[dependency-groups]`, `[tool.ruff]`, `[tool.pytest.ini_options]` in `code/pyproject.toml` |
| Tests next to the package, recorded inputs as fixtures, no network | `code/ingestion/tests/`, `tests/fixtures/` (kept byte-exact by `.gitattributes`) |
| Entry points declared in `pyproject.toml`, not ad-hoc scripts | `swx-noaa-live`, `swx-gfz`, `swx-omni` |

Differs: nothing. The older `uv init` stub in the repo root (`main.py`, `pyproject.toml`, `uv.lock`,
`.python-version`, `.venv`) was removed on 2026-11-14, so `code/` is the only project root (`decisions.md`).

## 2. Data store: `data/`

Sources: Cookiecutter Data Science (https://cookiecutter-data-science.drivendata.org/): `data/raw` is "the original,
immutable data dump", with intermediate and processed data apart; university research-data guides (e.g. University
of Toronto, https://library.utoronto.ca/researchdata/organizing-your-data): a README in the top data folder that
explains the structure.

| Practice | Here |
|---|---|
| Raw data immutable, never edited by hand | `data/raw/`: byte-for-byte copies, SHA-256 in `raw/manifest.parquet` |
| Derived data apart from raw and rebuildable from it | `data/normalized/` (versioned rows, provenance columns) |
| Data kept out of version control | `/data/*` in `.gitignore` |
| README describing the structure | `data/README.md` (the only tracked file there) |

Differs: the folder is called `normalized/`, not `processed/`. The name is part of the contract between ingestion
and platform (`code/CLAUDE.md`), so it stays.

## 3. Evaluation set: `evaluation/`

Sources: Gebru et al., "Datasheets for Datasets" (https://arxiv.org/abs/1803.09010): document motivation,
composition, collection process and recommended uses; C19 Data Collective documentation criteria
(https://c19datacollective.com/criteria/data-documentation/): README plus a data dictionary; DigitalOcean,
"Evaluation dataset best practices"
(https://docs.digitalocean.com/products/evaluations/concepts/evaluation-dataset-best-practices/): keep the evaluation
set fixed between runs, or differences between runs cannot be attributed.

| Practice | Here |
|---|---|
| How and why the set was composed | `event_set/zestaw_zdarzen_zasady.md` |
| Data dictionary for every column | `event_set/data_dictionary.md` |
| The set is generated by a script from recorded inputs, not edited by hand | `zestaw_zdarzen_build.py`, fixed seed 2026 |
| Stable IDs and a version per record | `id`, `wersja`; removed IDs are never reused |
| Fixed between runs; held-out part used once | DEV/TEST split, root `CLAUDE.md` invariant 5 |
| Provenance of every input | "Źródła" sheet of the XLSX, `MANIFEST_D*.md` in `dataset_research` |

Differs: inputs, scripts and outputs share one flat folder instead of `inputs/`, `scripts/`, `output/`. The rules
document links to its neighbours and the build script finds them by position; ten files with a README table stay
readable, so the split was not made.

## 4. Thesis text and LaTeX: `thesis/`

Sources: Overleaf, "How to Write a Thesis in LaTeX (Part 1): Basic Structure"
(https://www.overleaf.com/learn/latex/How_to_Write_a_Thesis_in_LaTeX_(Part_1):_Basic_Structure); texblog, "On
managing large documents" (https://texblog.org/2016/06/20/on-managing-large-documents); GitHub's `TeX.gitignore`
(https://github.com/github/gitignore/blob/main/TeX.gitignore).

| Practice | Here |
|---|---|
| One main file plus a preamble; one file per chapter; figures and bibliography apart | Layout written down in `thesis/latex/README.md`; no `.tex` file exists yet |
| Build output out of version control | `thesis/latex/.gitignore` |
| Unpublished text kept out of a public repository | `/thesis/*` in `.gitignore`; only the two folder guides are tracked |
| Outline and its sources kept with the text | `thesis/spis_tresci.md`, `thesis/spis_tresci_wzorce.md` |

Differs: no skeleton `.tex` files were created, because the template is not chosen and thesis wording must not be
invented (`thesis/CLAUDE.md`).

## 5. Project knowledge: `docs/`

Sources: adr.github.io (https://adr.github.io/): "the collection of ADRs created and maintained in a project
constitute its decision log", each record capturing a single decision and its rationale; TechTarget, "8 best
practices for creating architecture decision records"
(https://www.techtarget.com/searchapparchitecture/tip/4-best-practices-for-creating-architecture-decision-records):
keep them in the repository; "when a decision is superseded, the new ADR should reference the old one".

| Practice | Here |
|---|---|
| Decision log in the repository, next to the code | `docs/decisions.md` |
| Each decision dated, with rationale and affected files | Entry format of `decisions.md` |
| Never edit an old decision; a later one supersedes it | "A later entry wins"; old entries keep old paths |
| Open points apart from decisions | `docs/open_questions.md` |
| An index that says what to read for which task | `docs/README.md` |

Differs: one chronological file instead of one numbered file per decision. For a single author the single file is
easier to read in order; split it if it passes about 400 lines.

## 6. Knowledge base: `knowledge/` (advisor correspondence, sources, findings)

Sources: research-data file-naming guides (CASRAI,
https://casrai.org/guides/file-naming-and-folder-structure-conventions-for-research-data; TU Delft,
https://tu-delft-dcc.github.io/docs/data/data_collection/data_conventions.html): ISO 8601 dates (`YYYY-MM-DD`) so
files sort in time order, no spaces or special characters, three to five elements per name; Cookiecutter Data
Science (link above): a `references/` folder for data dictionaries, manuals and other explanatory materials.

| Practice | Here |
|---|---|
| Reference material in its own folder, apart from code and results | `knowledge/sources/` |
| An index of the reference files, so a file is found without opening it | `knowledge/sources/sources_index.md` |
| Consistent file names with the same elements in the same order | `<year>_<first_author>_<short_title>.pdf`; `<YYYY-MM-DD>.pdf` for e-mail threads |
| ISO dates in dated file names | `advisor/email_threads/2026-10-05.pdf`, `findings/2026-11-14_<topic>.md` |
| Dated, append-only notes of what was found (lab-notebook practice) | `knowledge/findings/`, one note per finding, superseded instead of rewritten |
| Records read-only, drafts apart | `advisor/email_threads/`, `advisor/presentations/` vs `advisor/emails_to_advisor/` |
| Private and copyrighted material out of version control | `/knowledge/advisor/*` and `/knowledge/sources/*` in `.gitignore` (the GitHub repo is public) |

Differs: `odpowiedz_prof_surma_final.txt`, `maile_surma.pdf` and `Prezentacja_temat_pracy.pptx` keep their names,
because `decisions.md` and the snapshot documents refer to them. The lab-notebook row is common practice, not taken
from one of the sources above.

## 7. Research archive: `dataset_research/`

Practice (same research-data guides): an archive is frozen, read-only and described by a README. Here: untouched
since October 2026, `README.md` in the folder and in `space_weather_decision/`, provenance in `MANIFEST_D*.md`.

## 8. Repository root

| Practice | Here |
|---|---|
| A README that maps the folders and gives the everyday commands | `README.md` |
| A README in every top-level folder | Yes, all seven |
| Line endings fixed by `.gitattributes`, not by each machine's git settings | `.gitattributes`: text as LF, `*.cmd` as CRLF, fixtures untouched |
| Secrets, data, private files and build output ignored | `.gitignore` |
| Folder and file names: lower case, underscores, no spaces | Yes, except a few legacy file names kept for references |

Differs: folder names inside `docs/` are Polish (`metodologia`, `zrodla_danych`, ...) while the top level is
English, because they mirror the shared folder of the Claude project.
